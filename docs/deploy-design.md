# 一键部署的设计思路

> 这份文档回答一个问题：**为什么这套部署是这个样子。**
>
> 具体命令、配置模板、参数都在 `scripts/install.sh` 里，本文不重复。这里只讲**分步的逻辑**——
> 每一步解决什么问题、为什么必须按这个顺序、失败时为什么必须停。
> 理解了这套思路，你就能自己改造它，而不是照抄。

---

## 一、核心命题

在**一台单机 VPS** 上，把 OpenClaw 从裸机变成**长期无人值守运行**的 AI agent 平台。

难点不在于"把容器跑起来"——那只要 `docker run` 一行。难点在于四件事：

1. **可重复**：任意一台新机器，跑一次就得到一致结果，不靠人工记忆和手工补漏。
2. **可失败**：部署过程中任何一步出错，必须**立刻停**，而不是留下半成品继续往下跑。
3. **可自愈**：部署完成后的长期运行中，故障要能被自动发现和修复，而不是等人发现。
4. **不裸奔**：密钥、端口、权限从第一次启动就是收敛的，不是"先跑起来再加固"。

整套设计围绕这四点展开。

---

## 二、分步思路：每一步在防什么

部署被切成有序的 10 步，顺序不是随意的——**后一步依赖前一步建立的前提**，所以顺序本身就是设计。

### 第 1 步 · 系统加固（Swap + 防火墙）

**在装任何东西之前先做**，原因：后面的容器和依赖需要内存余量，而防火墙必须在服务起来之前就位，否则会出现"服务已监听公网、规则还没配"的窗口。

**关键取舍——防火墙用保守策略**：
很多一键脚本会 `ufw --force reset` 图省事，但这会**清空用户机器上已有的规则**。如果这是台复用机器，可能直接切断现有业务甚至锁死 SSH。
所以这里**只增量添加、不改默认策略**：放行业务端口，`default deny` 只在"本来就没启用 ufw"时才设。

> 设计原则：**破坏性操作宁可少做一步，也不能替用户做决定。**

### 第 2 步 · 基础依赖

Docker / Nginx / Certbot 按需安装。**判断"是否已装"而不是无脑重装**——同一个脚本要在全新机器和已有环境上都安全。

### 第 3 步 · 目录结构

先建好所有目录，**并且立刻设定权限**。这一步的意义是：把"数据放哪、谁能读"变成**部署时就定死的契约**，而不是运行时随意落地。

`/data` 下的划分对应三类东西：状态（`state`）、配置与密钥（`etc`）、运维脚本（`scripts`）。权限从紧：密钥目录 `700`，可共享的工作区 `755`。

### 第 4 步 · 密钥与 Token 注入

**这是整个设计里最需要克制的一步。**

思路是：密钥**只写入一个文件**（`runtime.env`，权限 `600`），容器通过 `env_file` 读取，**绝不写进 compose 明文、绝不进 git、绝不打印到日志**。

同时生成一份**凭证摘要文件**——但摘要里**只写路径和读取命令，不写 Token 本身**。这样即便摘要被误传，也不泄露密钥。

> 设计原则：**让"拿不到明文"成为默认结果**，而不是靠"记得别说出去"。

### 第 5 步 · Gateway 容器

容器定义本身也遵循几条收敛原则：

- **端口只绑 `127.0.0.1`**：Gateway 永远不直接对公网暴露，外部访问一律经 Nginx 或 SSH 隧道。这是默认拒绝的姿态。
- **资源限额**：内存 / CPU / PID 三项都设上限。不是怕它用得多，而是怕**故障时它把宿主机拖死**——一台被拖死的宿主机，连登录排查的机会都没有。
- **健康检查**：容器状态不停留在"进程还在"，而是明确的 `healthy`。后续所有步骤（包括自愈）都以这个信号为准。

### 第 6 步 · 反向代理

有域名 → Nginx + Let's Encrypt 出 HTTPS，且**必须带 WebSocket 升级头**（OpenClaw 控制台是长连接，漏了这条会表现为"能打开但连不上"）。

无域名 → 退化为本地端口 + 建议走 SSH 隧道，**而不是把明文端口开到公网图方便**。

> 设计原则：**安全路径要能被"顺理成章地默认走"**，便捷路径得让人明确选择。

### 第 7～8 步 · 模型配置与 agent 上下文

模型配置只声明**白名单 provider**，不允许默认全开——插件/供应商全开是常见的攻击面和成本黑洞。

agent 的上下文文件（人格、策略、通知等）安装为**模板骨架**，用户后续自行填充。

> 注意：这些是**给使用者起步用的空骨架**，不是某台具体机器的运行配置。个人化的内容永远留在运行环境里，不进仓库。

### 第 9～10 步 · 备份与自检

部署的最后一步不是"启动成功"，而是**把长期运行的能力装上去**：

- **定时备份**：默认保留 7 份，防止"配置改坏无法回退"。
- **定时自检**：不是简单 `docker ps`，而是检查关键链路（端口、代理、DNS、沙箱等），异常时才告警。

> 设计原则：**部署的完成标志是"能自愈"，不是"能启动"。**

## 三、三条贯穿始终的原则

### 1. 失败即停，不盲目重试

每一步都带**最小验证**，通过才进下一步。失败 → 报告错误和日志 → **停**。

为什么重要：部署脚本最危险的失败模式不是"报错停下"，而是**"某步静默失败但继续跑"**——最后得到一个看起来跑起来、实际半残的系统，排查成本远高于直接失败。

### 2. 幂等

脚本可以**反复运行**，重复执行不产生副作用：已存在的配置不覆盖、已放的防火墙规则不重复加、目录已存在就跳过。

为什么重要：一键部署的真实使用场景是**"出问题了再跑一次"**。不幂等的脚本第二次运行就是灾难。

### 3. 配置与密钥分离

**配置**（什么模型、什么端口）进 git，可版本化、可 review。
**密钥**（API Key、Token）只存在运行环境的 `600` 文件里，永不进仓库。

这条线划清楚，仓库才能公开、部署才能安全。

---

## 四、这套思路的边界

诚实说清楚它**不**解决的问题：

- **不是安全沙箱**：Gateway 能操作宿主机是设计目标（它要管服务器），代价是它自身必须被信任。
- **单机假设**：整套设计的资源档位、备份、自愈都基于单机。多机编排不在范围内。
- **自愈有盲区**：自动巡检能发现"脚本明确检查的项"，发现不了"没被想到的故障类型"。

知道边界在哪，比假装没有边界更有用。
