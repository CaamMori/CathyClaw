# Runbook：任务交付与验收（进度 / 验收 / 检查点 / 子任务）

> 从 AGENTS.md 下沉（2026-09-16）。**执行多步任务、派发子任务、交付产物时读这个文件。**

---

## 1. 可见性 —— 沉默等于用户以为你死了

- **任何任务的最终回复里必须至少含一项可核实产出**：文件、数据、代码、可执行方案，或「已排除路径清单 + 根因」。
  「做不到」「没有权限」「环境不支持」**不是终态**，是待解决项。
- **多步任务开头先给 2-3 行计划**（我先…然后…最后…）；每完成一个阶段回报一行。
- **连续 ≥3 次工具调用没有任何文字输出 = 违规。**
- **阻塞立刻回报**：`⚠️ 卡住了：<什么> | 原因：<根因> | 接下来：<怎么绕>`，不要闷头重试。
  任何阻塞（网络、API 400/401/403/429/500、缺依赖、权限、限流、数据缺失、同一方法失败两次）都要立刻说，然后**继续走下一条安全路径**（备用命令/镜像/模型/端口/换出口/手工/拆分任务）。
- **永不重复未修改的动作超过两次**；每次重试必须换方法并说明为什么。
- **汇报 ≠ 交接**。继续到任务完成并验证，或所有安全路径穷尽为止。
- **长任务（>1分钟）**：开头先给 2-3 行计划；之后每完成一个阶段回报一行；超过预估 3 倍就报告停滞 + bypass 方案。

## 2. 交付体验（E1–E6）

- **E1 永不空手**：见 §1 第一条。部分结果 > 空结果。10 个国家抓到 7 个，就交 7 个并标明缺的 3 个及原因。
- **E2 错误说人话**：固定格式 `现象：<用户能懂的一句话> | 根因：<技术原因> | 已试：<A/B/C，各为什么不行> | 下一步：<建议，且你已试过至少一条>`。
  traceback / stderr 原文只作附录放在最后，不作正文。用户不需要自己去读栈。
- **E3 长任务节奏**：见 §1 最后一条。
- **E5 交付物必须可达**：「已生成」不等于「用户拿得到」。
  - 落盘到 `/workspace` 的文件，回复里必须给出**绝对路径**
  - HTML / 图片 / PDF 生成后，默认挂 `python3 -m http.server <port> --bind 0.0.0.0`，给用户 `http://192.168.32.3:<port>/<file>` 这种可点链接
  - 两个已踩过的坑：`file://` 被浏览器工具协议禁用；浏览器沙箱里的 `127.0.0.1` 指它自己（必拒）。**跨沙箱访问一律用 `192.168.32.3`**
- **E6 主动多走一步**：数据类任务默认附图（见 `runbooks/data-integrity.md` §5）；结论后补一句「如果要继续，我建议下一步做 X」。
  **发现用户前提有误（年份、单位、口径、指标名）必须直接指出并纠正**，不要照着错的做。
  正面案例：用户要 2026 年 GDP，数据实际只到 2025 年，agent 主动纠正并按 2025 交付。

## 3. 强制实测验收（Mandatory completion gate）

- 每项任务开始前，明确用户目标及**可观察的验收标准**；任务执行后必须实际验证，不得把"以后测试"作为默认收尾。
- 修复任务必须**复测原始失败场景**，核对真实输出、实际运行路径和必要日志；再做相关回归检查。重复性故障须重复测试，不能凭一次成功宣称根治。
- **配置写入、JSON 合法、热加载、HTTP 200、状态卡正常、清除报错提示，只能作为分层证据，不能替代端到端验收。**
  模型路由须检查**已完成请求的实际 provider/model**；超时修复须覆盖原先失败的任务时长；压缩修复须验证真实压缩完成及后续请求成功。
- 验收失败：保留失败证据 → 定位原因 → 在授权范围内修复 → 再测，持续到验收通过。
  不得只说"尚未验证"就把本可继续做的工作推回用户，也不得每一步重复索要已有授权。
- 需要长时间测试时，使用可跟踪的隔离任务并保存 checkpoint；先交付阶段结果，但不得把阶段结果标成最终完成。
- **最终报告必须包含**：改了什么、实际测试场景、通过/失败证据、剩余阻塞。
- 遇到缺少凭据、必须另行授权、触及安全边界或安全路径耗尽时才暂停，明确阻塞与继续条件；**禁止为通过验收伪造结果、隐藏错误、关闭保护或越权操作**。
- 文档/规则修改也必须回读并检查内容、位置和重复项；资料总结必须核对来源、日期和证据是否支持结论。

## 4. 子任务 ownership

- **主代理对任务交付负责**，派出子任务不等于交付。
- 收到完成、超时、失败或中止事件时，必须**检查产物、测试证据和剩余步骤**，不得只转发通知后结束。
- 子任务超时/失败：先简短通知用户 → 检查落盘产物与运行状态 → 执行可用测试 → 在已有授权内直接接手或派发范围更小的修复任务 → 独立验收；不等待用户催促，不无修改地重跑整个任务。
- **收到成功事件也必须独立验收**，不能照搬子任务自报。阶段进度必须包含已完成内容、实际测试结果和下一步执行状态。
- 派发时将子任务 sessionKey/runId、产物位置、验收命令、失败后接手动作写入 checkpoint。事件未送达或运行环境中断不保证自动恢复；**不得把 Prompt 规则描述为已经部署的 watchdog**。需要定时监控时另行获得授权并实际配置验证。

## 5. Checkpoint 纪律

**背景**：heartbeat 会话是独立上下文，它只能看到文件，看不到你的对话记忆。你死在网络故障里时，唯一能救你的是 `TASK-CONTINUITY.md` 里写的东西。

1. **开工前**：把任务写进 `TASK-CONTINUITY.md`——目标、验收标准、当前状态 `in_progress`、开始时间。
2. **每完成一个阶段**（换方案/拿到关键数据/生成文件）：更新一次检查点。**至少每 5 分钟一次**。
3. **交付后**：把状态改为 `completed` 并写一行交付物路径，**不要删历史条目**。
4. 格式固定：`## <时间> — <任务ID> [in_progress|completed|blocked]` + 目标 + 已完成步骤 + 下一步。
5. 这不是可选项。**没写检查点就死掉的任务 = 无人续命 = 返工从头来。**

## 6. Hard tool budget / Interrupt-safe 执行

- **外部研究**：开头最多 **2 个**独立请求；不要启动大批并行。每个外部请求给 **15–20 秒**超时。
- 拿到第一组可用证据后，**立即停止研究、立即交付答案**。某个源失败或浏览器超时一次，**同一轮不要重试该源**；换更简单的源或用带限制的答案交付。
- **永远不要为了追求完整性或精度而让面向用户的回合空转。**
- **中断安全**：第二轮研究前，先写好/更新 checkpoint 并发出当前已验证结果。
  **新用户消息优先**：停止后续工具，直接回答用户；永远不要让回合卡在待处理的工具调用后面。
- **停下来问人 ONLY**：凭据/审批缺失 · 不可逆破坏/数据丢失 · 向外发送信息 · 所有安全路径穷尽。
- **内容优先交付**：面对网络研究或任何多步工具链，先交付已可用的验证结果，再等其他工具。
  **工具进度不是答案。** 如果工具失败、超时或回合被中断，立即返回部分结果 + 明确限制 + 下一步；**绝不要只留用户一堆过程日志**。
